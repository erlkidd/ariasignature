# AriaSignature — руководство пользователя

Версия документа: 0.2.3.

## 1. Назначение

AriaSignature — локальная desktop-система для:
- диагностики дисков и хранения телеметрии;
- выполнения резервного копирования баз 1С по расписанию;
- публикации производимых данных через HTTP API для внешних интеграций.

Продукт рассчитан на установку у клиента с автономной работой после первичной настройки.

## 2. Компоненты и режим работы

- `AriaSignature.Service` — фоновый сервис Windows. Выполняет сбор телеметрии, планирование и выполнение задач архивации, публикацию API.
- `AriaSignature.UI` — desktop-панель управления (WPF + WebView2) для администрирования.
- Локальная БД SQLite — хранение настроек, задач, журналов и срезов диагностики.

Ключевой принцип: источником телеметрии, backup-исполнения и журнала является сервис.
UI не выполняет эти процессы самостоятельно.

## 3. Что делает сервис после установки

- запускается автоматически вместе с ОС;
- продолжает выполнять расписание архивирования без открытия UI;
- продолжает формировать диагностические данные;
- предоставляет данные через `/api/v1` для внешнего потребителя.

## 4. Требования к рабочей станции

- Windows 10/11 x64;
- Microsoft Edge WebView2 Runtime;
- права администратора для установки/обновления;
- сетевой доступ к ресурсам, куда пишутся архивы;
- для MSSQL-задач: доступ учетной записи сервиса к SQL Server и целевой БД.

## 5. Интерфейс панели

### 5.1 Накопители

- список физических дисков с текущим статусом;
- карточка выбранного диска (емкость, температура, SMART/ресурс, счетчики);
- история SMART;
- ручное обновление среза.

Источники телеметрии:
- primary: low-level SMART/NVMe через `smartctl`;
- fallback: WMI (`MSStorageDriver_*`, `Win32_DiskDrive`);
- fallback: Storage Reliability (`MSFT_StorageReliabilityCounter`).

В карточке диска выводятся:
- фактически использованный источник (`smartctl`, `WMI`, `StorageReliability`);
- оценка достоверности телеметрии (`telemetryConfidence`, 0..100);
- причина деградации при частичной телеметрии (`telemetryDegradationReason`).

### 5.2 Архивация

- создание задач типов `file` (`.1CD`) и `msSql`;
- визуальная настройка расписания и расширенный Quartz-режим;
- проверка MSSQL-подключения перед сохранением;
- ручной запуск задач;
- журнал выполнения и фильтрация.

### 5.3 Настройки

- параметры API (порт);
- параметры диагностического расписания;
- тема интерфейса;
- автозапуск UI в трей.

## 6. Модель эксплуатации

1. Установить продукт.
2. Проверить статус сервиса и доступность API.
3. Настроить задачи архивирования через UI.
4. Проверить тестовый запуск задачи и появление записей в журнале.
5. Подключить внешний контур к API сервиса для чтения данных и статусов.

Дальнейшая работа выполняется сервисом автоматически; UI используется для изменений и контроля.

## 7. Отдача данных во внешний контур

- Базовый API-префикс: `/api/v1`.
- Основные разделы:
  - `/status`;
  - `/disks`, `/disks/{id}`, `/disks/{id}/smart`;
  - `/backups`, `/backups/logs`.

Формат ошибок API: `application/problem+json`.

## 8. Ограничения и примечания

- Точность SMART зависит от поддержки диска/контроллера/драйвера и уровня доступа.
- Отсутствие отдельных полей телеметрии допустимо для части оборудования.
- Смена API-порта требует перезапуска сервиса.
