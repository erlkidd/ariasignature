# ТЗ + ЛТ на расширение 1С для AriaSignature

Версия: 1.0 (зафиксированная целевая модель)  
Статус: в разработку

---

## 1. Цель

Сделать расширение 1С, которое:
- работает с данными AriaSignature по API;
- позволяет отбираться по контрагенту;
- показывает данные в одной обработке (одна форма, две вкладки: "Диски" и "Архивации");
- пишет данные в два отдельных регистра (по дискам и по архивациям) через два отдельных документа;
- строит два отчета по месяцам с отбором по контрагенту.

Ключевое правило учета данных:
- учет реализуется только по схеме `Документы -> Движения в регистрах`;
- прямая запись из обработки/API в регистры без документов не допускается.

---

## 2. Жесткая функциональная модель (фиксируем без вариантов)

В расширении используются:
1. Два основных справочника:
   - `КонтрагентыAria`
   - `КомпьютерыAria`
2. Одна основная обработка:
   - `МониторAria`
   - одна форма обработки
   - две вкладки: `Диски` и `Архивации`
3. Два документа:
   - `ДокументДискиAria` (движения только в регистр дисков)
   - `ДокументАрхивацииAria` (движения только в регистр архиваций)
4. Два регистра сведений:
   - `РегистрДискиAria`
   - `РегистрАрхивацииAria`
5. Два отчета:
   - `ОтчетДискиAria`
   - `ОтчетАрхивацииAria`

Любые альтернативы "один документ на оба регистра" или "без документов, сразу в регистр" в рамках этого ТЗ не применяются.

Отдельно фиксируем:
- используем одновременно и документы, и регистры;
- документы являются источником движений, регистры — источником отчетов и аналитики.

---

## 3. Архитектурные ограничения

1. Не использовать БСП.
2. Не использовать код/модули/функционал типовых конфигураций.
3. Все доработки реализуются внутри расширения.
4. Изменения форм — только программно, без интерактивной правки макета.
5. Для внешних интеграций (HTTP, Telegram, E-mail и др.) использовать OpenIntegrations.
6. Поддержка Melezh обязательна.

---

## 4. Интеграционный контракт AriaSignature (базовый для реализации)

Базовый URL:
- `http://<host>:<port>/api/v1`
- порт по умолчанию: `5160`

Авторизация (если включена в AriaSignature):
- `Authorization: Bearer <token>`
- или `X-Aria-Api-Key: <token>`

Используемые endpoints:
- `GET /status`
- `GET /system`
- `GET /disks`
- `GET /backups`
- `GET /backups/logs`

Требования к обработке ошибок:
- поддержка `application/problem+json`;
- обработка 401/404/500, сетевых ошибок и таймаутов;
- запись текста ошибки в журнал/служебное сообщение расширения.

---

## 5. Объекты метаданных и их назначение

## 5.1 Справочник `КонтрагентыAria`

Назначение:
- хранить список контрагентов для мониторинга.

Минимальные реквизиты:
- `Наименование` (обязательный)

Форма элемента:
- программно добавленная табличная область/список связанных компьютеров из `КомпьютерыAria`;
- чтение без редактирования.

## 5.2 Справочник `КомпьютерыAria`

Назначение:
- хранить точки подключения к AriaSignature.

Минимальные реквизиты:
- `HostName` (обязательный)
- `IPУстройства` (обязательный)
- `Контрагент` (ссылка на `КонтрагентыAria`, обязательный)
- `ПортAPI` (по умолчанию 5160)
- `ТокенAPI` (опционально)
- `Активен` (булево)

## 5.3 Обработка `МониторAria`

Назначение:
- единое рабочее место оператора.

Структура:
- одна форма;
- поле отбора по контрагенту (`КонтрагентыAria`);
- вкладка `Диски`;
- вкладка `Архивации`.

Сценарий работы:
1. Пользователь выбирает контрагента.
2. Обработка определяет связанные компьютеры из `КомпьютерыAria`.
3. По каждому компьютеру получает данные по API AriaSignature.
4. Отображает данные по вкладкам (`Диски` / `Архивации`).
5. По командам создает и проводит нужный документ для записи в соответствующий регистр.

## 5.4 Документ `ДокументДискиAria`

Назначение:
- фиксировать прием данных о дисках;
- формировать движения только в `РегистрДискиAria`.

Минимальные реквизиты шапки:
- `Контрагент`
- `Компьютер`
- `ДатаВремяПолучения`
- `СтатусПолучения`
- `ТекстОшибки`

ТЧ:
- строки по дискам, полученные из API.

## 5.5 Документ `ДокументАрхивацииAria`

Назначение:
- фиксировать прием данных по задачам/логам архивации;
- формировать движения только в `РегистрАрхивацииAria`.

Минимальные реквизиты шапки:
- `Контрагент`
- `Компьютер`
- `ДатаВремяПолучения`
- `СтатусПолучения`
- `ТекстОшибки`

ТЧ:
- строки задач архивации и/или логов запусков из API.

## 5.6 Регистр сведений `РегистрДискиAria`

Источник данных:
- движения документа `ДокументДискиAria`.

Минимальная структура:
- Измерения: `Период`, `Контрагент`, `Компьютер`, `ИдентификаторДиска`
- Ресурсы/реквизиты: модель, интерфейс, температура, health, статус, источник телеметрии, причина деградации.

## 5.7 Регистр сведений `РегистрАрхивацииAria`

Источник данных:
- движения документа `ДокументАрхивацииAria`.

Минимальная структура:
- Измерения: `Период`, `Контрагент`, `Компьютер`, `ИдентификаторЗадачи`
- Ресурсы/реквизиты: наименование задачи, статус выполнения, размер, текст результата, время запуска/окончания.

## 5.8 Отчет `ОтчетДискиAria`

Источник:
- `РегистрДискиAria`.

Обязательные отборы:
- `Контрагент`
- `Месяц` (период)

## 5.9 Отчет `ОтчетАрхивацииAria`

Источник:
- `РегистрАрхивацииAria`.

Обязательные отборы:
- `Контрагент`
- `Месяц` (период)

---

## 6. Регламентное и ручное заполнение

Должно быть два режима:
1. Ручной:
   - из обработки `МониторAria` кнопками:
     - "Обновить диски" (создать/провести `ДокументДискиAria`);
     - "Обновить архивации" (создать/провести `ДокументАрхивацииAria`).
2. Регламентный:
   - задание по расписанию выполняет тот же процесс автоматически по активным компьютерам.

Требование:
- ошибка по одному компьютеру не останавливает обработку остальных.

---

## 7. Стандарты кодирования и именования

1. Префикс объектов расширения: `Aria` в конце имени (как зафиксировано в этой модели).
2. Изменения типовых форм — только программные.
3. Код расширения в модулях помечать служебным комментарием с автором, датой и номером ЛТ.
4. Для новых ролей:
   - роль на чтение;
   - роль на изменение.
5. Изменения запросов делать точечно (без тотальной замены типового текста).

## 9. Матрица приемочных проверок (минимум)

1. Для выбранного контрагента корректно подтягиваются его компьютеры.
2. Вкладка `Диски` показывает данные API по связанным компьютерам.
3. Вкладка `Архивации` показывает данные API по связанным компьютерам.
4. Ручной запуск создает и проводит `ДокументДискиAria`.
5. Ручной запуск создает и проводит `ДокументАрхивацииAria`.
6. Движения документов попадают строго в "свой" регистр.
7. Регламентный сбор обрабатывает несколько компьютеров, включая недоступный.
8. Отчет по дискам корректно работает по отбору "Контрагент + Месяц".
9. Отчет по архивации корректно работает по отбору "Контрагент + Месяц".
10. Ошибки API (401/404/500/таймаут) отображаются и логируются.

## 10. Definition of Done

Расширение считается готовым, если:
- реализованы ЛТ-01 ... ЛТ-15;
- структура объектов соответствует разделам 2 и 5 без отклонений;
- обработка реализована как одна форма с двумя вкладками;
- данные в регистры пишутся через два отдельных документа;
- не используется прямая запись в регистры в обход документов;
- отчеты работают в разрезе месяца и контрагента;
- интеграции выполняются через OpenIntegrations + Melezh;
- пройдена матрица приемки из раздела 9.

## 12. Упрощенная документация API AriaSignature (для разработки расширения 1С)

Этот раздел дублирует в упрощенном виде самое важное из `docs/API.md`, чтобы разработку расширения можно было вести по одному документу.

## 12.1 Базовые параметры

- Базовый путь: `/api/v1`
- Базовый URL: `http://<IP_или_DNS_узла>:<порт>/api/v1`
- Порт по умолчанию: `5160`
- Формат: `application/json`

## 12.2 Авторизация

Если в AriaSignature задан токен удаленного API:
- `Authorization: Bearer <token>`
- или `X-Aria-Api-Key: <token>`

Если токен не задан, запросы из сети (при открытом порте) проходят без заголовка.

## 12.3 Контракт ошибок

- `400` — ошибка валидации (`application/problem+json`)
- `401` — нет/неверный токен
- `404` — ресурс не найден
- `500` — внутренняя ошибка сервиса

В расширении 1С ошибки надо:
- показывать пользователю в понятном виде;
- сохранять технический текст в документ/служебный журнал.

## 12.4 Минимальный набор endpoints для нашего расширения

### 1) Проверка доступности узла
- `GET /status`
- Использование: проверить, что агент доступен и отвечает.

### 2) Общая информация об узле
- `GET /system`
- Использование: карточка компьютера (host, сеть, ОС и т.д.).

### 3) Диски
- `GET /disks`
- Использование: заполнение вкладки `Диски`, документа `ДокументДискиAria`, регистра `РегистрДискиAria`.

### 4) Задачи архивации
- `GET /backups`
- Использование: список задач архивации на узле.

### 5) Логи архивации
- `GET /backups/logs`
- Опциональные параметры:
  - `status=Succeeded|Failed`
  - `from=<ISO datetime>`
  - `to=<ISO datetime>`
- Использование: заполнение вкладки `Архивации`, документа `ДокументАрхивацииAria`, регистра `РегистрАрхивацииAria`.

## 12.5 Как расширение 1С должно взаимодействовать с API (рабочий алгоритм)

1. По выбранному `КонтрагентыAria` получить список `КомпьютерыAria`.
2. Для каждого активного компьютера:
   - вызвать `GET /status`;
   - при успехе вызвать `GET /disks`, `GET /backups`, `GET /backups/logs`;
   - при ошибке зафиксировать ошибку и перейти к следующему компьютеру.
3. По данным дисков создать/провести `ДокументДискиAria` -> движения в `РегистрДискиAria`.
4. По данным архивации создать/провести `ДокументАрхивацииAria` -> движения в `РегистрАрхивацииAria`.
5. Показать результат в форме обработки (две вкладки) и в отчетах.

## 12.6 Быстрые примеры HTTP-запросов

```http
GET http://192.168.1.50:5160/api/v1/status
GET http://192.168.1.50:5160/api/v1/disks
GET http://192.168.1.50:5160/api/v1/backups
GET http://192.168.1.50:5160/api/v1/backups/logs?status=Failed
```

С токеном:

```http
GET http://192.168.1.50:5160/api/v1/system
Authorization: Bearer <token>
```

## 12.7 Что НЕ используем в рамках текущего MVP расширения

- Управляющие write-endpoints AriaSignature (`POST/PUT/DELETE` по задачам) как обязательную часть MVP.
- Сложные сценарии настройки агента через `/settings` из 1С.

Они могут быть добавлены позже отдельным этапом без изменения базовой модели "2 документа + 2 регистра + 1 обработка".
